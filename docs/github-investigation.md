# クローンせずにGitHubを調査する

## 操作

1. 「プロジェクト」の「GitHubから」を開きます。
2. 調査対象を選択し、「選択したリポジトリを調査」を押します。1回に最大50件です。
3. ブランチ・参照名は任意指定できます。空欄なら各リポジトリの既定ブランチを使用します。指定した参照が存在しないリポジトリは取得失敗として表示します。
4. 保存された調査結果を選択し、「選択したGitHub結果を照合」を押すと、更新候補と既知の注意情報をまとめて調べられます。この照合ではパッケージ名・版を公開レジストリとOSVへ送信します。
5. リポジトリ名を押すと、取得ファイル・依存宣言・固定ツール・選択中のデバイス環境の導入版・照合結果を確認できます。
6. 詳細の「更新方針を作成」で、変更候補、固定ツールの確認、宣言された検証、未確認事項を保存します。

クローン先の指定は不要です。クローンして実際に更新・検証したい場合は、同じリポジトリ一覧の保存先を開いて「クローン」を使用できます。

## 取得する情報

GitHub CLIの有効な認証を使い、アクセス可能なリポジトリをREST APIの`user/repos`から先頭300件まで取得します。利用者のアカウント名・ホーム・ドライブを固定しません。認証情報はGitHub CLIで管理し、アプリでトークンを取得・保存しません。

対象の参照をコミットへ解決し、そのコミットのツリーとblob SHAを指定して、対応する設定・依存・ロックファイルだけを読み取ります。サブフォルダー内も調べます。取得途中でブランチが動いても、異なるコミットのファイルは混ぜません。

- 対応対象はmise、Node、Python／uv、Cargoの設定・ロックと、GitHub Actionsのワークフローです。
- Node・Python・Cargoの依存解析と更新・OSV照合は、ローカル調査と共通の処理を使用します。モノレポでは宣言元とpnpm importerの対応を保持します。
- Actionsは`uses`の指定を抽出します。Actions自身の最新版・脆弱性照合は未対応です。
- 仮想環境の実体、実行中のプロセス、プロジェクトコードは調べません。`.env`・アプリのソース一式など、対象外のファイルは取得しません。
- `.npmrc`はレジストリ指定だけを解析し、認証用の行を調査結果へ保存しません。

取得した本文はメモリ上で解析し、SQLiteには対象リポジトリ・参照・コミット・ファイルのSHA／状態・解析結果を保存します。生のファイル本文やGit作業ツリーは保存しません。

## 更新方針の意味

これは実行用のコマンド列ではなく、静的な更新方針です。GitHub上のファイルやローカル環境を変更せず、テスト・ビルド・依存解決も実行しません。依存更新は同一メジャー内を優先し、0.xでは同一minorを維持します。

方針を作成する直前に対象の参照を再確認します。コミットが変わっていれば再調査を求めます。再調査でコミットや取得内容が変わった場合、以前の照合結果を消し、保存済み方針を「再調査が必要」と表示します。

デバイス比較は、GitHubに記述された要求と、選択中のWindows／WSL環境で取得した導入版を並べるものです。制約の充足や、そのプロジェクトが実際に使用する実行ファイルまで証明しません。未調査の環境は未検出と区別します。

## 上限・未確認事項

- 1回50リポジトリ、1リポジトリ200対象ファイル、1ファイル1.5MB、合計16MBまでです。外部コマンドの応答には別途サイズ・時間の上限があります。
- GitHubのツリー一覧が省略された場合は完了扱いにしません。上限やリンク・サブモジュールなどで未取得の対象があれば明示し、完全に取得できるまで方針作成を拒否します。
- 解析未対応の形式や、公開サービスの照合失敗は未確認のまま表示します。Yarn・従来のrequirements形式の完全解析、非公開レジストリの自動照合は未対応です。
- 一部のリポジトリの失敗は他の調査を中断しません。失敗した対象の古い結果は書き換えず、直近の失敗を別に表示します。
- 「対応設定なし」は依存が存在しないという判定ではありません。最新版、既知の脆弱性ゼロ、互換性、実行検証済みを一括して保証する表示は行いません。

## 開発時の検証

`pnpm test:github`は、GET以外のAPIやクローン操作を拒否する模擬GitHub CLIで、実バックエンドを検証します。複数取得、一部失敗、モノレポ解析、照合、方針保存、対象コミットの更新、再調査による古い方針の無効化、Git作業ツリーが作られないことを確認します。ネイティブ通し試験にも画面からの取得・照合・方針作成を追加しています。

実際のGitHub APIでも、本リポジトリの作業ブランチから10個の設定・ロックファイルを取得して解析できることを確認しました。GitHubへの書き込みは行っていません。

## 調査結果と更新の配置

「プロジェクト」はローカルとGitHubの共通一覧です。同じリポジトリをまとめ、Windows／WSLの作業場所やGitHubの参照は別々に保持します。「比較・登録する環境」を変えても一覧は消えません。

保存した更新方針は「更新」の「計画・進行状況」に表示します。関連する作業場所を選ぶと、リモート、GitHubの現在のコミット、ローカルのコミット、未コミット変更を再確認します。一致した場合だけ作業環境確認済みとし、プロジェクト詳細で再照合と検証選択を行って実行計画を作成します。自動でブランチを切り替えたり作業内容を書き換えたりはしません。

更新方針の「GitHubから作業環境を用意」は、その方針のリポジトリ・参照を引き継ぎます。新規クローンでは調査したコミットをdetached HEADで開き、プロジェクト詳細へ移動します。「元の更新方針で作業環境を確認」から一致を再確認し、通常の更新計画で作業ブランチを作ります。対象参照が更新済みならクローン前に再調査を求めます。既存フォルダーへの上書きは行いません。
