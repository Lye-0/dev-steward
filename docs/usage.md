# Dev Steward

開発ツールの配置・バージョンと、プロジェクトの依存関係を結び付けて管理するデスクトップアプリです。

## 起動

ビルド済みの `dev-steward.exe` を起動します。Node・Python・Rust・mise・uvは、アプリの起動には不要です。WindowsにはWebView2 Runtimeが必要です。

開発時はリポジトリのルートで実行します。

```powershell
mise install
pnpm install --frozen-lockfile
pnpm tauri dev
```

Rustはrustupから、rust-toolchain.tomlに固定した版を使用します。miseと二重管理しません。

配布用実行ファイルのビルド：

```powershell
pnpm tauri build --no-bundle
```

Windows x64版は `target/release/dev-steward.exe` に作成されます。開発サーバーは不要です。現時点では署名・ストア公開・自動アップデートは設定していません。

## 最初の操作

1. 「環境を調査」で管理ツールとランタイムを取得します。
2. WSLも使う場合は「設定 → Windows・WSLの環境を検出」を実行し、右上で対象を選びます。検出時にWSLが起動する場合があります。
3. 「プロジェクト → フォルダーを登録」でリポジトリ、または複数リポジトリを含むフォルダーを指定します。
4. プロジェクトを選び、固定ツール、パッケージ、仮想環境を確認します。
5. 更新・脆弱性の照合を行い、対象と検証を選んで計画を作ります。照合ではパッケージ名・版が公開レジストリ・OSVへ送信されます。
6. 「更新」の「計画・進行状況」で対象・コマンド・未確認事項を読み、一工程ずつ実行します。

## GitHub

GitHubからの取得・PR操作はGitHub CLIを利用します。必要な場合にインストールして `gh auth login` で認証してください。利用者がアクセスできるリポジトリ（最大300件）を一覧表示します。認証情報をアプリへ入力する必要はありません。

「プロジェクト」の「GitHubから」では、クローンせずに必要な設定・ロックファイルだけを取得し、更新候補の照合と静的な更新方針を作成できます。複数リポジトリの選択と任意のブランチ・参照名に対応します。[操作と対応範囲](github-investigation.md)を参照してください。実際に更新・検証する場合は、クローンしてローカルの作業環境を用意します。GitHub上の静的調査をローカル動作確認済みとは表示しません。

更新前に既定ブランチを最新へ合わせたい場合は「既定ブランチへの同期を計画」を使用します。その後に再調査・更新候補の再照合をしてください。更新ブランチは、計画を作った時点のローカルHEADから開始します。

PR作成まで含めるには、更新計画の作成時に「検証後のコミット・プッシュ・PR作成も計画に含める」を選択します。実行する工程を事前に確認できます。作成したPRは自動マージしません。全CIの成功とコミットの一致を確認できた場合に、別のマージ計画を作成できます。

## 配置と固定版

「開発環境」はmise・uv・rustupなど管理元ごとに別の表を表示します。検索はすべての分類に適用されます。詳細で配置先と設定元を確認できます。対応する追加の管理元と検出方法は [tool-discovery.md](tool-discovery.md) を参照してください。関連プロジェクトは名前や宣言からの関連候補であり、実行確認とは別です。

「デバイスのツールと指定を揃える」で、導入済みの版へプロジェクトの指定を変更する計画を作成できます。pnpmはmiseの指定とpackageManagerを同期し、既存のdevEnginesも合わせます。Pythonはuvプロジェクトでのpin・sync、Rustはrust-toolchain.tomlを使用します。変更後は検証を実行してください。

MCPの起動先は設定画面でJSON／TOMLの設定ファイルを指定して静的に調べます。MCPの接続試験や専用MCP仮想環境の自動移行は、この版では行いません。

## 旧版の削除

Windowsのmise管理版は、インストール済み・既定で無効な対象の詳細から「旧版の削除可否を確認」へ進めます。管理元、登録フォルダー、MCP設定、PATH、実行中プロセスを確認できた場合だけ削除計画が作られます。調査範囲外の利用は、利用者自身でも確認してください。

Python、WSL、OS用・アプリ同梱のランタイムは自動削除の対象外です。キャッシュや作業ツリーの一括削除もしません。

## 失敗・中断時

- ログとGit差分を確認します。途中の変更は自動で元に戻しません。
- ブランチ・依存ファイル・仮想環境など、部分的な変更が残る場合があります。
- 必要な修正・退避を行い、再調査して新しい計画を作成してください。
- 失敗した計画の自動リトライは行いません。
- アプリを終了した場合、実行中だった工程は次回「結果不明」と表示されます。

スクリプトが出力した任意の秘密情報まで完全に除去できるわけではありません。秘密情報を表示するスクリプトを検証対象にしないでください。

## 検証コマンド（開発用）

```powershell
pnpm test
pnpm build
cargo test -p steward-core --locked
cargo clippy -p steward-core --all-targets --locked -- -D warnings
cargo build -p steward-core --bin steward
pnpm test:update
pnpm test:discovery
pnpm test:github
cargo build -p dev-steward
pnpm test:e2e
pnpm tauri build --no-bundle
node scripts/release-smoke.mjs
```

通し試験は一時ディレクトリ内に独立したリポジトリとデータベースを作成します。更新試験では小さな公開パッケージを取得します。GitHubへのプッシュ・PR作成・本物のツール削除は行いません。ネイティブ試験はWindows／WebView2向けです。

### Windowsのネイティブ試験の起動設定

試験スクリプトは `--data-dir <独立した絶対パス> --automation-port <ポート>` を明示してアプリを起動します。通常起動ではデバッグ用ポートを有効にしません。自動試験用ポートは専用データディレクトリを指定した場合だけ受け付け、WebViewのプロファイルもその配下に分離します。

管理者権限のWebView2は環境変数 `WEBVIEW2_*` の上書きを無視するため、試験用引数はWebView作成APIへ直接渡します（[Microsoftの説明](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5640)）。マシン全体のレジストリ設定を変更する必要はありません。

起動前にプロセスが終了した場合は終了コードを報告し、タイムアウトでは最後の接続エラーを含めます。標準出力・標準エラーは `test-results/native-smoke-startup.log` と `test-results/release-smoke-startup.log` に保存し、CIの検証用成果物から確認できます。
