# 開発環境・プロジェクト統合管理アプリ 計画書

更新日：2026-10-24（日本時間）

状態：実装開始前に合意した原計画です。アプリ名は、その後 Dev Steward（dev-steward）に決定しました。現在の実装・検証状況は [status.md](status.md)、構成は [architecture.md](architecture.md)、利用方法は [usage.md](usage.md) を参照してください。

## 1. 目的

デバイスにインストールされた開発ツールと、各プロジェクトが必要とするツール・依存パッケージをまとめて管理するデスクトップアプリを開発する。

単に最新版を一覧表示するだけでなく、次の質問に根拠付きで答え、更新・検証・不要な旧版の整理へつなげる。

- 何が、どのバージョンで、どこにインストールされているか。
- 誰が管理し、どのプロジェクトやアプリが実際に使用しているか。
- 更新の重要性は何か。互換性について何が確認できているか。
- プロジェクトの要求を踏まえ、デバイスのツールをどう更新すべきか。
- どの旧版を残す必要があり、どの旧版が削除候補になるか。
- 何を実行し、どこまで成功し、何が未確認か。

## 2. 必須条件

### 2.1 特定のPCに依存しない

このPC専用のアプリにはしない。ユーザー名、ホームディレクトリ、ドライブ、リポジトリの親フォルダー、WSLのユーザー名・ディストリビューション名をハードコードしない。

管理ファイルやインストール先は、OSのディレクトリ取得機能、管理ツールへの問い合わせ、環境変数、明示設定、設定の優先順位から検出する。標準パスだけを唯一の正解とせず、独自の配置も扱う。

- 未検出・権限不足・未対応・調査失敗を区別する。
- 自動検出できない対象は手動登録できる。
- 同じツールの複数インストールと、PATHで実際に選ばれる実行ファイルを区別する。
- Windows、macOS、Linuxに共通のデータ構造を用い、OS固有処理を分離する。
- 最初の対応環境はWindows＋WSL。他OSへの対応は後続段階とし、初期版の対応済み環境とは混同しない。
- 将来の複数PC対応に備え、データにデバイス識別子を持たせる。別PCの遠隔操作や同期は初期版の必須機能にしない。

### 2.2 アプリ自身は管理対象のランタイムに依存しない

配布したアプリの起動に、ユーザーがインストールしたmise、uv、Node.js、Python、Rust、Cの開発環境を要求しない。OS側のWebViewなど、配布方式に伴う前提条件は別途明示する。

開発時にmiseなどを利用することと、配布後の起動依存は分離する。miseやuvは外部の操作対象として呼び出す。

管理対象のツールが未導入・破損・更新中でも、アプリ自体は起動でき、取得済み情報、診断結果、復旧手順を表示できるようにする。

### 2.3 独自のランタイム配置を増やさない

PythonやNodeをアプリ独自のフォルダーへ無条件に再配置しない。既存の管理元を尊重する。

| 対象                       | 基本方針                                                 |
| -------------------------- | -------------------------------------------------------- |
| 開発用Python本体           | uv管理を推奨。実際の保存先は設定・問い合わせで取得       |
| Python仮想環境             | プロジェクトまたは用途ごとの環境。既存配置を把握して扱う |
| Node・pnpm・Javaなど       | miseなど、検出した管理元を通じて管理                     |
| Windowsアプリ              | WinGetなど、そのインストール元に適した方法で更新         |
| OS用Python・システムツール | OSのパッケージ管理を維持                                 |
| アプリ同梱ランタイム       | 配布元のアプリ更新に従う                                 |

「可能ならuvへ移す」は移行方針の一つとして設定できるが、OS用・アプリ同梱などを一律に移行しない。

## 3. 管理する情報

### 3.1 デバイスと環境

Windowsと各WSLディストリビューションを別の実行環境として識別する。OS、アーキテクチャ、管理元、インストール版、配置先、実行ファイル、PATH、shim、リンク先、検出日時を記録する。

同じ名前・バージョンでも、異なる環境にある実体は別管理とする。WSLからWindows側の設定を読んだ場合などは、設定の所在と実行環境の不一致を説明する。

### 3.2 プロジェクト

リポジトリの所在、リモート、既定ブランチ、Gitの変更状態、固定ツール、依存宣言、ロックファイル、ワークスペース、検証方法を把握する。

初期の重点対象はmise設定、Node系のpackage.json・主要ロックファイル、Pythonのpyproject.toml・uv.lock・バージョン指定・仮想環境。その他の形式やエコシステムは連携部を追加して拡張する。

モノレポではルートと各ワークスペースを関連付け、同じ依存を単純に重複計上しない。別の制約を無理に一つへ統一しない。

### 3.3 実際の利用関係

ツール本体、ランチャー、仮想環境、プロジェクト設定、MCP起動設定を関連付ける。

例：MCPの起動設定 → 専用仮想環境 → uv管理Python → Python本体の実体。

一覧に同じPythonが複数表示されても、リンク・ランチャーと本体を区別する。Pythonの仮想環境は本体の重複インストールとして扱わない。

各関係には根拠、調査範囲、最終確認日時を持たせる。「設定で要求される」「実際に選ばれる」「実行確認済み」は別の情報とする。

## 4. プロジェクトの取り込み

### ローカル

利用者が指定したフォルダーからクローン済みリポジトリを検出する。個別登録も可能にする。worktree、サブモジュール、過去のスナップショットを識別し、通常の現行プロジェクトと混同しない。

### GitHub

認証した利用者がアクセスできるリポジトリを取得し、選択して登録・クローンできるようにする。ローカルクローンとの対応はパス名だけでなくリモート情報などから判断する。

GitHub上だけの静的調査と、ローカルでの依存解決・実行検証を区別する。GitHub上の調査だけで、デバイス上の動作確認済みとは表示しない。

認証方式・最小権限・資格情報の保管方法は実装前に確定する。資格情報をログやリポジトリに保存しない。

## 5. 更新判断

初期の推奨方針は「同一メジャー内の更新を優先し、メジャー更新はセキュリティ、サポート終了、必要な機能などの理由がある場合に提案する」。プロジェクトごとに例外・保留・固定理由を記録できるようにする。

更新候補には次を表示する。

- 現在版・候補版・対象環境・管理元。
- 更新理由と重要性。セキュリティ修正、サポート、バグ修正など。
- 影響するプロジェクト・仮想環境・アプリ。
- 変更する設定、必要なコマンド、検証内容、旧版の扱い。
- 根拠の出典と取得日時、未確認事項。

同一メジャーでも互換性を保証しない。以下の検証状況を個別に保持して表示する。

1. 更新候補を検出。
2. 宣言されたバージョン制約を満たす。
3. 依存関係の解決に成功。
4. ローカルのテスト・ビルドに成功。
5. 対象コミットのCIに成功。
6. 必要な実起動・MCP接続・GPUなどの確認に成功。

全対象に同一の検証が必要なわけではない。更新内容に必要な確認を選ぶ。CIの成功は実行対象のコミットと対応付ける。

脆弱性情報はOSVなど、ツールのサポート状況や変更内容は公式情報を照合する。「既知の問題を検出しなかった」「照合できなかった」「未調査」を区別する。

AIは説明、変更内容の要約、移行案の補助に利用できるが、AIを必須の起動依存にはしない。バージョン・参照・操作可否は構造化した証拠と規則を中心に判定する。外部送信する情報は利用者が把握・制御できるようにする。

## 6. 更新の実行

基本の流れ：

調査 → 計画・差分の確認 → 必要な新バージョンの導入 → 設定・依存の更新 → 検証 → コミット・PR → CI確認 → 利用関係の再調査 → 不要な旧版の整理。

- 実行前に対象、コマンド、作業ディレクトリ、環境、変更予定を提示する。
- 未コミット変更や利用者のデータを保護し、無断で上書き・削除しない。
- 調査のために未知のプロジェクトコードやインストールスクリプトを無条件で実行しない。静的調査とコードを実行する検証を分離する。
- ブランチ、コミット文、PRの説明、マージ方法は設定可能にする。今回のチャットの手順を全利用者へ固定しない。
- PR説明は簡潔な箇条書きを既定案とする。
- 自動マージ・旧版削除は対象と条件を明示して設定する。一定時間の経過だけをCI成功とは扱わない。
- READMEなど依存更新と無関係の変更を無条件に含めない。対象外ファイルを方針として設定できるようにする。
- 実行履歴にコマンド、終了コード、変更差分、検証結果、日時を保存する。機密情報は伏せる。
- 失敗・中断時は完了工程と残工程を表示し、状態を再確認して再開する。
- ファイル変更の復元と、インストーラー・外部サービスへの操作の取り消しを区別する。すべてを完全にロールバックできるとは表示しない。

### 管理ツール自身の更新

miseやuvの本体更新は、そのツールを利用するアプリ内ジョブを止め、導入元に適した方法で実行し、実行ファイルを再検出して確認する。

使用中ファイルや外部プロセスによるロックを検出した場合は、終了・再起動などの必要な対応を示す。アプリが独立していることを理由に、すべてのロックを解消できるとは想定しない。

## 7. 旧版・配置の整理

プロジェクト更新の完了と、旧版を削除できる状態を別々に判定する。

削除候補の確認対象は、管理ツールの未使用判定、登録プロジェクトの要求、仮想環境の参照、MCP設定、PATH・リンク、実行中プロセスなど。調査対象外や取得失敗があれば、完全な未使用とは断定しない。

削除は可能な限り管理元のアンインストール機能を使う。手動の削除・移動では解決した絶対パスと対象範囲を検証する。

独自配置から標準管理へ移す場合は、新環境作成、依存導入、参照切り替え、必要な実動作確認の後で旧環境を整理する。単純なフォルダー移動で仮想環境を壊さないようにする。

キャッシュ、実体、ランチャー、仮想環境、作業ツリーを分けて扱う。ハードリンクなどにより論理サイズと実際の解放量が異なる点を考慮する。

| 画面         | 目的                                                        |
| ------------ | ----------------------------------------------------------- |
| 全体状況     | 更新の優先順位、影響範囲、未確認事項を把握                  |
| 環境         | OS・WSL別のインストール、配置、利用先、実効バージョンを確認 |
| プロジェクト | 固定ツール、依存パッケージ、ワークスペース、検証状況を確認  |

詳細なUI設計は未実施。名称、配色、レイアウトは後続の設計で決める。

## 9. 技術構成

Rustを採用する方針。Cと比較し、メモリ安全性、並列処理の扱いやすさ、保守性を重視する。ただしRustだけで誤った対象への更新・削除を防げるわけではなく、操作の検証を別途実装する。

| 構成要素         | 採用案・役割                                |
| ---------------- | ------------------------------------------- |
| デスクトップ基盤 | Tauri 2                                     |
| 画面             | React／TypeScript                           |
| 処理部分         | Rust：調査、計画、CLI実行、ファイル操作     |
| ローカルデータ   | SQLite：調査結果、利用関係、計画、実行履歴  |
| 管理ツール連携   | mise、uv、WinGet、APTなどの連携部           |
| プロジェクト連携 | Git、GitHub、パッケージ管理ツール、検証処理 |
| 実行環境連携     | Windows、WSL。将来macOS・Linuxを追加        |

画面から任意のシェル文字列を直接実行する構成を避ける。操作を型付きの要求として受け、バックエンドで対象・引数・権限・環境を検証する。

CLIの対応バージョン・機能を検出し、構造化出力を優先する。特定バージョンだけの出力形式に依存しない。連携部が未対応の場合は、取得不能を正常な取得結果として扱わない。

同じ管理元やロックファイルへの競合操作は直列化する。別環境の独立した調査は並列化できる設計とする。

Renovateの依存検出・更新機能は再利用候補。必須採用とはせず、初期の対応範囲、実行負荷、配布方法を調べて判断する。

## 10. 開発段階と完成条件

### 第1段階：配置と利用関係の可視化

Windows＋WSL、mise・uv・WinGet、ローカルのNode／Pythonプロジェクトを重点対象にする。APTはOS管理の識別・保護を先行し、更新実行は対応範囲を別途決める。

完成条件：

- 別ユーザー名、別ドライブ、標準外の管理先、複数WSLでも検出できる。
- ランチャー・実体・仮想環境を識別できる。
- 作業ディレクトリによる設定の切り替わりを説明できる。
- 各対象の利用先と、調査できなかった範囲を示せる。
- 管理対象のmise・uvなどがなくてもアプリが起動する。

### 第2段階：根拠付きの更新提案

最新版・脆弱性・制約を照合し、デバイスとプロジェクトを横断する更新計画を作る。GitHubからのプロジェクト取り込みに対応する。

完成条件：候補版、更新理由、影響先、変更予定、必要な検証、保留理由を表示できる。「未確認」を互換性確認済みとして扱わない。

### 第3段階：更新・検証・整理の実行

新バージョン導入、プロジェクト更新、テスト、PR、CI確認、旧版整理へ進む。対象と条件を設定した自動化を追加する。

完成条件：実行前の差分確認、失敗時の停止と再開、利用者の変更保護、実行結果の追跡、削除前の再確認ができる。

### 後続の拡張

macOS・Linux、追加のパッケージ管理系、複数PCの比較、任意のAI補助、定期調査など。第1段階へ一括して詰め込まない。

## 11. 次に確定する事項

- アプリ名と開発リポジトリの作成先。
- 第1段階で対応するCLI・設定形式・対応バージョンの一覧。
- 利用関係のデータモデルと検出の優先順位。
- GitHubの認証・資格情報管理方式。
- 調査・更新・コード実行・削除の権限と自動化設定。
- 配布形式、署名、アプリ自身の更新経路。

次の設計作業は第1段階の仕様とデータモデルを具体化すること。現時点では実装、ツール更新、GitHubへの書き込みは開始しない。
